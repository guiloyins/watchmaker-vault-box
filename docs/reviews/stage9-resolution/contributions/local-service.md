# Local USB service v1

**Candidate normative file: `docs/specs/LOCAL_SERVICE_V1.md`.** This is the proposed S9-03 interface, not an implemented tool or a completed hardware check. It defines local serial messages and operator attestations; [protocol v1](PROTOCOL_V1.md) continues to own network messages and recovery ordering. No network schema, fixture, capability or message changes are introduced.

## 1. Boundary and framing

`tools/fw-provision` and `tools/box-service` use one implementation, `tools/firmware/local_service.py`. The firmware boundary is `vault_service.hpp/.cpp`; box operations dispatch to `box_service.cpp` through the single actuator owner. Both wrappers require an explicit `--port` and `--device-id`. They inspect the connected identity before a mutation and refuse a mismatch. Never select the first enumerated port, reset the board merely to open a port, or automatically flash/provision a discovered device.

Use a dedicated USB serial application stream, **115200 baud, eight data bits, no parity, one stop bit, no flow control**. These settings define the UART adapter case; a verified native USB CDC backend provides the same byte stream. The actual connector, USB implementation and board pins remain profile gates. Opening/closing the port must not intentionally toggle reset/boot-control lines. Verify that behavior on each selected adapter. Logs and boot chatter are not valid service frames; production service mode disables credential-bearing logging and does not mix debug text into this stream.

One frame is one UTF-8 JSON object followed by one LF byte. Emit compact JSON with no literal newline in a string. Accept an optional single CR immediately before LF, counting it toward the limit. Requests are at most **4096 bytes excluding LF**; responses at most **8192 bytes excluding LF**. Reject duplicate keys, invalid UTF-8, trailing JSON, nonobjects, nonintegral numeric values, excessive depth, unexpected keys and invalid enum values. Object/array nesting is at most eight, including the root; each object has at most 32 members and each array at most 32 elements. IDs match `[A-Za-z0-9_-]{1,64}`. Ordinary text is at most 256 UTF-8 bytes and excludes C0/C1 control codepoints (U+0000–001F and U+007F–009F); the only larger string is the provisioning CA PEM, at most 2048 bytes. PEM may contain its required LF line breaks as JSON-escaped `\n`, explicitly exempt from the ordinary Text control-character exclusion; arbitrary other control characters remain invalid. Integers are exact mathematical values 0–9007199254740991 unless a narrower range is stated; `1.0` and `1e0` may normalize to 1, but nonintegral values are never rounded. `PositiveInt` excludes zero; `Hex64` is exactly 64 lowercase hexadecimal digits; `Text` follows the 256-byte limit. Booleans are literal booleans. Null is allowed only where specified. These are local contract choices, independent of network frame limits.

Allow one outstanding request and no unsolicited response. Parse incrementally into bounded storage. From the first byte, a frame has a 2000 ms assembly deadline. On oversized, incomplete or malformed input, discard through the next LF, emit one bounded error with `request_id:null` if an identity cannot be safely parsed, and resume framing. Never echo input fragments. Admit at most ten complete requests per second, burst two; excess receives `rate_limited`. `stop` must set the volatile stop/inhibit flag ahead of queued ordinary service requests; rate limiting and a full receipt cache cannot delay the physical stop. Successful durable acknowledgement still requires its normal write. The actuator scheduler and its deadlines never run in the serial parser or wait for serial output.

The wrapper opens in binary/no-echo mode, validates both frame directions, and uses a 3000 ms response deadline. Read-only requests may be retried at most twice. Mutation timeout enters the readback procedure in §3; a timeout is never evidence that the operation did not commit. A motion command's response deadline does not extend its motion deadline. All framing limits have boundary and limit-plus-one tests.

## 2. Envelopes and shared values

Every request has exactly these fields:

```json
{"sv":1,"type":"request","request_id":"req_PLACEHOLDER","device_id":"box_PLACEHOLDER","box_boot_id":"boot_PLACEHOLDER","operation_id":null,"expected_revision":null,"command":"inspect","args":{"section":"status"}}
```

`request_id` is a fresh random 128-bit ID for this transport exchange. The physical box uses all commands below. Controllers support only `inspect` sections status/provisioning, `operation.get`, `provision.set`, `stop`, `reboot` and `service.exit`; other commands return `unsupported_command`. For controllers, status reports inactive actuator/empty journal fields and `stop` neutralizes/disables input. Controller initialization sets `motion_frozen:false`; controller exit requires provisioned configuration, current binding and an observed neutral input baseline, with neither `service.prepare` nor a preparation-operation ID nor box calibration/locked verification required. Its commit records the exit ID, clears service/input inhibition and retains `motion_frozen:false`; it grants no box motion capability. Entering common provisioning service needs no host key. `box_boot_id` must match the current device boot for a new mutation; it may be null for `inspect`, `operation.get` and `stop`. The stable provisioned identity must still match. Unprovisioned devices return a stable factory-local identity derived from the available chip identifier and require that exact identity as `device_id` for first provisioning; this is an operator selection aid, not an authentication credential. Successful first provisioning changes the identity only on the required reboot. After that reboot, the wrapper expects exactly the provision file’s `device_id` for read-only operation lookup; it preserves the original factory-ID request in its protected operation file and never resends it under the new identity. A provisioned identity cannot be changed by `provision.set`.

Read-only requests use null `operation_id` and `expected_revision`. Mutations use both fields as specified in §3. Every response has exactly:

```json
{"sv":1,"type":"result","request_id":"req_PLACEHOLDER","device_id":"box_PLACEHOLDER","box_boot_id":"boot_PLACEHOLDER","operation_id":null,"service_revision":7,"status":"ok","code":"ok","data":{"storage_version":1,"service_revision":7,"service_epoch":1,"device_id":"box_PLACEHOLDER","box_boot_id":"boot_PLACEHOLDER","binding":null,"service_inhibited":true,"motion_frozen":true,"motor_active":false,"outputs_disabled":true,"active_motion_operation_id":null,"preparation_operation_id":null,"readiness":{"arm_id":null,"armed_session_id":null,"calibration_valid":false,"start_verified":false},"position":{"latch_position":"unknown","position_basis":"unverified"},"journal_count":0,"active_local_record_id":null,"clear_operation_id":null,"storage_fault":null}}
```

`status` is `ok | pending | rejected | uncertain`. `ok` for a mutation means its specified durable decision committed; it does not imply motion or physical verification. `pending` means durable admission succeeded and a local bounded operation is still running. `uncertain` means the durable outcome cannot presently be established; gameplay remains inhibited. `operation.get` returns the original committed decision plus its separately updated completion, never executes it. Errors have `data:{}` except `revision_conflict` (`{expected_revision:CURRENT}`), `wrong_device` (`{actual_device_id:ID}`), and `stale_boot` (`{actual_box_boot_id:ID}`). `Code` is `ok` or one of the following errors; motion completion additionally uses `stopped`, `reboot_interrupted`, `freshness_lost`, `travel_timeout`, `limit_fault`, `driver_fault`. Error codes are `invalid_frame`, `unsupported_version`, `invalid_args`, `unsupported_command`, `wrong_device`, `stale_boot`, `rate_limited`, `busy`, `revision_conflict`, `operation_conflict`, `receipt_expired`, `operation_unknown`, `storage_error`, `commit_uncertain`, `not_in_service`, `recovery_required`, `identity_mismatch`, `binding_mismatch`, `reboot_required`, `session_fence_required`, `motion_frozen`, `unreconciled_history`, `profile_unverified`, `calibration_invalid`, `reference_required`, `sensor_unavailable`, `travel_limit`, or `provisioning_locked`. Errors expose no secret, free-form parser input or host access key.

The following exact objects are reused below. Required fields are not omitted:

- `Operator = {operator_id:ID, observation:Text}`. It records who claims to have performed the physical/local comparison. A USB caller can supply it; the firmware does not authenticate a host account from this value.
- `Fingerprint = {session_id:ID, action:"set_latch", target:"released"}`. `session_id` is the original command session. The original round is host metadata, not part of the v1 firmware fingerprint.
- `Intent = {game_id:ID, command_id:ID, intended_box_id:ID, original_session_id:ID, original_round_id:PositiveInt, fingerprint:Fingerprint}`. Require matching session fields and intended box identity; preserve the host-only game/round values as operator-attested metadata.
- `Binding = {box_boot_id:ID, connection_id:ID, current_session_id:ID}`. It describes the current authenticated network welcome, not the old command session. A disconnected box has null `binding`; do not manufacture IDs.
- `LocalEvidence = {local_record_id:ID, service_epoch:PositiveInt, seal_operation_id:OperationID, box_boot_id:ID, connection_id:ID, current_session_id:ID}`. Host closing evidence adds the fresh network `status_seq` to these values; local inspection cannot fabricate that sequence.
- `Preparation = {request_id:ID,recovery_id:ID,recovery_generation:PositiveInt,current_session_id:ID,game_id:ID,command_id:ID,intended_box_id:ID,original_session_id:ID,original_round_id:PositiveInt,fingerprint:Fingerprint,prior_recovery_id:ID|null,committed_at_ms:Int}`. These flat fields are the host preparation receipt in [Implementation contracts](IMPLEMENTATION_CONTRACTS.md); its original identity fields reconstruct `Intent` without renaming. Initial Begin uses null prior recovery; replacement names the prior recovery. These are fields copied from a committed host receipt. Retried host requests return their original receipt even when superseded; an old receipt cannot advance local recovery.
- `HostCurrent = {session_id:ID,recovery_id:ID|null,recovery_generation:Int,disposition_id:ID|null}` is the separate current result of authorized host `read_operation`; generation is zero iff recovery ID is null, otherwise positive. The operator transcribes and compares it; a historical preparation receipt never asserts a still-current session.
- `Disposition = {request_id:ID,disposition_id:ID,disposition:"closed_no_replay",recovery_id:ID,recovery_generation:PositiveInt,game_id:ID,command_id:ID,intended_box_id:ID,original_session_id:ID,original_round_id:PositiveInt,fingerprint:Fingerprint,closed_session_id:ID,local_record_id:ID,service_epoch:PositiveInt,seal_operation_id:OperationID,box_boot_id:ID,connection_id:ID,status_seq:PositiveInt,committed_at_ms:Int}`. These flat fields are the host Close receipt; `closed_session_id` matches the sealed `Binding.current_session_id`. Timestamps are audit-only and supply no freshness or authority. Host authorization, durable Close arbitration and the binding-valid query happen on the host. The operator attests this committed receipt locally; the device does not claim cryptographic verification of it.

## 3. Durable operation identity, retry and readback

Maintain a never-reset durable `service_revision`, initially zero. `service_epoch` is another durable counter, initialized to one with inhibited/frozen first-use service, incremented only on a later transition from normal operation into inhibited service; repeated entry while inhibited retains it. Recovery, reboot and history clear preserve the epoch, and exit records the epoch it closes. `service_revision` is independent of network revisions, journal count and `service_epoch`. A new mutation supplies `expected_revision` from inspection and `operation_id = svc_<16 lowercase hexadecimal digits>_<32 random lowercase hexadecimal digits>`. The encoded sequence must equal `expected_revision + 1` and fit the integer bound. The random suffix supplies 128 random bits. The revision prefix makes an expired ID permanently ineligible for another admission, even if a caller changes its expected revision. At exhaustion, fail closed; wrapping is prohibited.

Keep 64 durable compact service receipts, independent of the 32 gameplay-command slots. A receipt is `{storage_version:1, operation_id, request_sha256, expected_revision, resulting_revision, command, decision, completion}`. `decision` is the original `{status,code,data}` (at most 2048 encoded bytes); `completion` is null or `{state:"complete"|"uncertain"|"failed",code:Code,steps_executed:Int|null}`. The entire receipt is at most 3072 bytes. Hash the normalized typed request (`sv`, selected device identity, boot condition, command, operation ID, expected revision and args), excluding transport request ID, using the implementation plan’s `Vault.JSON.canonical/1` / `vault::json::canonical`: recursively sorted ASCII keys, integer decimal notation, no whitespace, standard quote/backslash and short control escapes, remaining controls as lowercase `\u00xx`, other UTF-8 unchanged, slash unescaped and no Unicode normalization. Do not expose this hash or retain plaintext provisioning credentials in receipts. Persist only the hash and nonsecret result. Recovery/clear records retain the operation IDs they reference after the rolling receipt ages out. Clearing gameplay history preserves the service revision and receipt ledger.

Look up a retained receipt before boot/revision/readiness admission checks. Same ID and same normalized request returns the saved decision and current completion without reexecuting. A changed known request is `operation_conflict`. Public readback omits internal `request_sha256`; `Receipt` in a response means the same fields except that digest. An absent ID whose encoded sequence is at or below the durable revision returns `receipt_expired`, never executes, and requires inspection of the named state/record. An unseen ID with the wrong next sequence or expected revision returns `revision_conflict`. Syntax/domain rejection before admission consumes no revision and has no durable success receipt. The wrapper never changes a rejected or uncertain request under its existing ID.

Serialize admitted mutations. Atomically commit their receipt, incremented revision and state change before reporting success. Before motion, this commit records the reserved operation and its exact finite budget; immediately before the first step recheck current boot, service epoch, binding/reference generation, inhibit/freeze and safety limits. No NVS/SQLite write, serial send or retry blocks active stepping. Readback uses the published in-memory durable snapshot while motion runs; required final persistence begins after outputs are inactive. Stop/de-energize before committing final motion outcome. Completion updates are correlated to the existing operation ID and do not allocate another service revision; the storage adapter’s transaction revision may still advance. A duplicate admission can read an existing running outcome but cannot start it again. On crash, a retained in-flight service motion becomes `uncertain`, position/reference become unknown/invalid, and no motion resumes.

The wrapper retains a mode-0600 operation file before transmission: `{file_version:1,operation_id,expected_revision,request_without_secrets,result:null|Receipt}`; use `--operation-file PATH`, owner-only parent, exclusive creation, no symlink following. For provisioning the file holds the protected source path and source-file digest instead of secret values. Reopening a file validates the identical request/source and reads back its ID; it never generates a replacement ID. Keep the original protected source until provisioning is resolved.

After any lost reply, failed durable read or uncertain commit, issue `operation.get` with that same ID, then inspect relevant state. Do not admit further ordinary mutations while a store outcome remains unknown. A verified absent receipt with unchanged durable revision and intact required records permits retransmission of the exact non-motion request only. **Motion is never retransmitted automatically**, including a verified absent admission; require fresh human intent, fresh inspection and a new operation ID for any subsequent physical action. Readback cannot turn an uncertain historical movement into nonexecution. `stop` remains available to establish the volatile stop and attempt a durable inhibit even when ordinary mutation admission is blocked. Missing/corrupt/unsupported required records never mean initialized empty storage.

## 5. Inspect and current-versus-historical data

`inspect/status` data is exactly `{storage_version:1,service_revision,service_epoch,device_id,box_boot_id,binding,service_inhibited:Boolean,motion_frozen:Boolean,motor_active:Boolean,outputs_disabled:Boolean,active_motion_operation_id:OperationID|null,preparation_operation_id:OperationID|null,readiness:{arm_id:ID|null,armed_session_id:ID|null,calibration_valid:Boolean,start_verified:Boolean},position:{latch_position:"locked"|"released"|"unknown",position_basis:"endstop"|"manual_verified"|"unverified"},journal_count:Int,active_local_record_id:ID|null,clear_operation_id:OperationID|null,storage_fault:Code|null}`. Journal count is 0–32. A fault can prevent trusted durable details from being returned; report it rather than substitute empty state.

`inspect/command` returns `{command_id,journal_observation:"present"|"not_present_current_journal",record:JournalRecord|null,current:{binding,motor_active,outputs_disabled,readiness,position}}`. `JournalRecord` is `{storage_version:1,command_id,fingerprint,reserved_arm_id:ID,outcome:"accepted"|"motion_complete"|"position_confirmed"|"uncertain"|"failed",failure_code:ID|null,command_confirmation:{basis:"endstop"|"manual_verified",box_boot_id:ID}|null,local_record_id:ID|null}`. Confirmation is nonnull iff the retained outcome is `position_confirmed`; an old confirmation remains historical even when the present position differs. A record is at most 2048 bytes. `inspect/journal` returns `{entry:JournalRecord|null,next_after_command_id:ID|null}`. The final page's cursor is null, including the empty journal. The wrapper fails inspection if any frame would exceed the response budget.

`inspect/recovery` returns `{record:Reconciliation}`. `inspect/clear` returns `{clear:ClearHeader|null}`; a clear entry request returns `{entry:ClearEntry}` or `invalid_args` if outside the saved count. Physical position, a terminal old command and historical uncertainty are separate values. Administrative acknowledgement never changes an execution outcome. Terminal/idle Reset remains available only when recovery has not begun; once it has, late terminal evidence cannot bypass host Close and local acknowledgement.

## 6. Durable local records

All records below have storage version one; missing/corrupt/unsupported required records fault/inhibit. Initialization is explicit for a genuinely uninitialized device; erased state after prior provisioning is not permission to initialize silently. Flash storage transaction layout is an implementation detail of `vault_storage`, but each acknowledged atomic generation must reload exactly these records or fail closed.

`ServiceControl` is exactly `{storage_version:1,service_revision:Int,service_epoch:PositiveInt,service_inhibited:Boolean,motion_frozen:Boolean,entry_operation_id:OperationID|null,preparation_operation_id:OperationID|null,exit_operation_id:OperationID|null,stop_reason:"maintenance"|"lost_host_key"|"history_clear"|"recovery"|null,active_local_record_id:ID|null,clear_operation_id:OperationID|null,provisioning_operation_id:OperationID|null,provisioning_reboot_required:Boolean,inflight_motion:ServiceMotion|null}` and is at most 4096 bytes. For a box, explicit first initialization sets revision zero, epoch one, inhibited/frozen true, all IDs/motion null and provisioning reboot false. Controller initialization uses the same values except `motion_frozen:false` as defined in §2. Persisted `service_inhibited:false` cannot override boot's inactive/no-arm/no-reference initialization. Every nonnull referenced required record must exist and match. For a box, exit requires an existing preparation ID and `motion_frozen:false`; its commit records the exit operation ID and clears only service inhibition, retaining the already-false freeze. Stop/new service entry, seal and history clear invalidate the preparation ID and current reference/start evidence. `service.prepare` records the new preparation ID; the explicit first recovery-entry or replacement-attestation transition may also supply its own ID when entering authorized preparation, as specified in the command table. Reboot preserves the preparation ID but never restores live reference/start evidence. Controllers have no actuator preparation requirement: their initialized freeze is false, and exit retains it false while enforcing their neutral-input gate. This object contains no live connection, reference or start-verification authority.

`ServiceMotion` is exactly `{operation_id:OperationID,command:"motion.jog"|"motion.home"|"motion.relock"|"motion.release_test",admission_box_boot_id:ID,service_epoch:PositiveInt,calibration_revision:PositiveInt,reference_revision:Int,binding:Binding|null,direction:"forward"|"reverse",max_steps:PositiveInt,rate_steps_s:PositiveInt,timeout_ms:PositiveInt,home_sensor_id:ID|null}`. It records the admitted finite budget and source generation, never a resumable timeline. A commissioning jog may use reference revision zero and null binding; other operations enforce their table gates. Retain its receipt while outstanding; no other ordinary mutations may evict it. On boot, stop/de-energize, mark that receipt's completion uncertain with `reboot_interrupted`, clear in-flight admission after committing that outcome, and invalidate all live reference/start/arm state. If exact executed step count was not durable, `steps_executed` is null rather than invented zero; completion permits `Int|null`. Null means unobserved, not no movement.

`Reconciliation` is exactly `{storage_version:1,local_record_id:ID,intent:Intent,recovery_id:ID,recovery_generation:PositiveInt,host_request_id:ID,recovery_session_id:ID,service_epoch:PositiveInt,entry_operation_id:OperationID,entry_box_boot_id:ID,journal_observation:"present"|"not_present_current_journal",observed_outcome:"accepted"|"motion_complete"|"position_confirmed"|"uncertain"|"failed"|null,operator:Operator,seal:{operation_id:OperationID,binding:Binding,operator:Operator}|null,acknowledgement:{operation_id:OperationID,disposition_id:ID,host_request_id:ID,status_seq:PositiveInt,operator:Operator}|null,replacement:{operation_id:OperationID,prior_recovery_id:ID,prior_recovery_generation:PositiveInt,prior_seal_operation_id:OperationID|null}|null}`. The seal describes local stopped/disarmed frozen evidence; host Close retains the later sequenced network status separately. Reconciliation is at most 4096 bytes. A replaced generation's host receipt/history remains durably retained on the host; the local bounded record keeps the immediate supersession linkage and current authoritative generation, never promotes an old receipt.

Attach up to 32 reconciliation records to the existing 32 accepted entries without consuming an extra command slot. Keep **one** absent-ID recovery record outside that capacity, never an invented accepted entry. Its `observed_outcome` is null; absence proves only the current journal observation. A different absent-ID recovery cannot overwrite an unacknowledged active one. Replacement for the same intent updates the same stable `local_record_id`; a completed/acknowledged absent record can be retired only after its operator-visible disposition and any clear authorization are retained. Queries and service stop remain available at full gameplay capacity.

`ClearHeader = {storage_version:1,clear_operation_id:OperationID,pre_clear_box_boot_id:ID,pre_clear_session_id:ID,service_epoch:PositiveInt,retained_host_history:true,entry_count:Int,phase:"prepared"|"erasing"|"awaiting_fence"|"fence_complete"|"preparing"|"exited",fence_binding:Binding|null,exit_operation_id:OperationID|null}`. Entry count is 0–33. Each `ClearEntry` is `{intent:Intent,local_record_id:ID,recovery_id:ID,recovery_generation:PositiveInt,service_epoch:PositiveInt,seal_operation_id:OperationID,seal_binding:Binding,disposition_id:ID,host_close_request_id:ID,status_seq:PositiveInt,acknowledgement_operation_id:OperationID,operator_id:ID}` and is at most 2048 bytes. Copy every reconciliation acknowledgement needed to authorize later exit, including the absent-ID record. Together header and all entries are at most 98304 bytes. With 64-character ordinary IDs, 53-character service operation IDs, maximum integers and three 256-byte observations consisting entirely of escapable printable characters, the complete reconciliation is 4009 encoded bytes; the complete compact clear entry is 1473 bytes. These fit the declared caps without truncating required evidence. C0/C1-free observation text is required to preserve this bound. Full 33-entry clear authorization remains below its budget; serial inspection stays one entry per frame. No free-text observation is required in this compact copy; the original host disposition and evidence remain permanent.

Before erase, commit the external complete clear record and read it back, then freeze/invalidate all reserved movement and erase the gameplay entries. Do not reconstruct authorization from an empty journal. Partial erase/reboot remains inhibited and frozen; readback identifies the same `clear_operation_id`. The storage owner may resume only its durably admitted idempotent erase work after reload, with no motor effect; inspection never starts an unrelated operation. Record `awaiting_fence` only after erasure verification. Each erase transaction atomically clears `ServiceControl.active_local_record_id` if that transaction erases its referenced reconciliation, while preserving `clear_operation_id`, the full copied authorization, inhibition and freeze. This is a same-service-revision storage transition, not another local operation admission. The acknowledged absent-ID record is also copied and explicitly erased; it never survives as a dangling pointer or becomes an accepted journal entry. Only after all journal/attached reconciliation records and any included acknowledged absent record are erased may the clear phase become `awaiting_fence`. `service.prepare(clear)` resolves its authorization through the matching complete clear record, not a reconstructed reconciliation. A fresh boot and a different authenticated host session are mandatory before `history.fence`; preserve the exact old pair until then. `service.prepare(clear)` uses the retained copied authorizations, then fresh local reference/locked verification and durable `service.exit` finish the fence. Retain the completed clear authorization through that exit, including every interruption. Neither Reset nor clear supplies a new arm or permits an old envelope to use new bindings.

## 7. Calibration and provisioning

`Calibration = {storage_version:1,profile_sha256:Hex64,mechanism_id:ID,mode:"commissioning"|"validated",sequence_id:ID,step_unit:"sequence_transition",release_direction:"forward"|"reverse",release_steps:PositiveInt,max_travel_steps:PositiveInt,max_rate_steps_s:PositiveInt,motion_timeout_ms:PositiveInt,home:null|{sensor_id:ID,max_steps:PositiveInt,max_rate_steps_s:PositiveInt,timeout_ms:PositiveInt},measurement_ref:ID}`. Firmware allocates monotonically increasing calibration revision on successful `calibration.set`. A sequence transition means one advance in the verified profile's coil sequence; neither this unit nor a motor label establishes shaft angle or a gear ratio. `release_steps <= max_travel_steps`; timeout is at most 8000 ms; a validated release must meet the at-most-3000-ms design stroke. Rate/step bounds must fit the verified actuator scheduler's tested integer range; profile validation rejects an unsupported range. Changing profile/mechanism/sequence invalidates compatibility.

Commissioning requires an evidence-backed finite budget for the accessible, unloaded test arrangement after electrical/profile/manual-release checks. It permits only bounded jog; it cannot claim final gameplay calibration or arm. Replace it with measured validated travel before release-test, relock or gameplay. There is no shipped nonzero default travel/rate. `home:null` means unavailable, regardless of a lid contact. Enabled homing needs installed verified endpoint sensing and its own measured travel/deadline; no repeated hard-stop driving. All motion clamps to the narrower requested/configured step, rate and deadline bounds and checks stop/freeze at admission and before each bounded step. A missed schedule budget stops instead of catching up.

`inspect/calibration` returns `{configuration:Calibration|null,calibration_revision:Int,reference:{revision:Int,box_boot_id:ID,calibration_revision:PositiveInt,method:"manual_verified"|"home_sensor"}|null,locked_verification:{binding:Binding,basis:"manual_verified"|"endstop",operation_id:OperationID}|null}`. Reboot/interruption invalidates reference; disconnect/session change invalidates locked verification and arm. A calibration file is configuration, not a current reference or physical observation. Service motion has its own deadline and serial-control-loss stop: stop at a bounded step on a detectable local transport close, or after 1500 ms without a valid local `operation.get`/`inspect` request while service motion is active. Poll at 100 ms. Gameplay continues to use the separate 1500 ms authenticated-server watchdog. Losing either relevant authority never starts/resumes motion.

Provisioning files are UTF-8 JSON with exactly the following shape, at most 4096 bytes; placeholder values are intentionally unusable:

```json
{
  "file_version": 1,
  "device_id": "DEVICE_ID_FROM_HOST_REGISTRATION",
  "device_class": "box",
  "allowed_roles": [],
  "profile_sha256": "REPLACE_WITH_64_LOWERCASE_HEX_PROFILE_HASH",
  "wifi": {"ssid": "REPLACE_WITH_SSID", "password": "REPLACE_WITH_PASSWORD"},
  "server": {
    "url": "wss://HOST_PLACEHOLDER/device/v1",
    "trusted_lan_development": false,
    "ca_pem": "REPLACE_WITH_APPROVED_PEM_CA_CERTIFICATE"
  },
  "device_secret_hex": "REPLACE_WITH_64_LOWERCASE_HEX_256_BIT_DEVICE_SECRET"
}
```

`Provisioning` is this object without `file_version`. `device_class` is box/controller; box roles must be `[]`, controller roles a nonempty unique subset of `a,b,c,d` matching host registration (firmware roles grant no host permission). SSID is 1–32 UTF-8 bytes; password 0–63 bytes; URL at most 256 bytes with exact `/device/v1`, no userinfo/query/fragment. `wss` requires nonempty PEM CA, hostname verification and `trusted_lan_development:false`; `ws` requires `trusted_lan_development:true` and `ca_pem:null`. CA PEM is at most 2048 bytes; secret is exactly 64 lowercase hex digits. Reject placeholders, malformed keys, unresolved profile hashes and unverified profile/device targets. Keep host access/session secrets out of this file.

Use an existing owner-only directory and a mode-0600 regular file. The wrapper verifies ownership/mode, rejects symlinks and reads through the checked handle. It neither prints secret fields nor places secrets on command-line arguments, in stderr/debug logs or in output receipts. Runtime credential/config files and operation files are ignored by source control. Provisioning is over physically controlled local USB; it does not claim channel encryption or tamper resistance. A reconfiguration preserves identity/journal/recovery state, keeps the device inhibited, and requires deliberate reboot/readback; registration and Wi-Fi values are never silently regenerated. Use a separate stopped maintenance procedure for intentional credential replacement; this interface does not promise host/device atomic key rotation.

## 8. Exact wrapper interface and operator sequence

The planned wrappers accept only the following shared options: `--port PORT --device-id ID`; mutation commands also require `--operation-file PATH`. Read-only output is JSON, redacted by shape, and can be saved with shell redirection. JSON argument files contain exactly the corresponding table `args` object; wrapper validation is strict. The wrapper reads revision/boot immediately before creating a new operation file, then persists that file and sends one request. A revision race refuses and preserves the file; it does not silently assign another operation. For an existing operation file it performs readback first. Exit codes: 0 completed success/readback, 2 validation/rejection, 3 pending, 4 uncertain/expired receipt requiring inspection, 5 serial/unavailable error. Pending motion is polled without replay through its one operation file; process exit/interrupt invokes a best-effort stop, whose success must be read back separately.

```sh

tools/box-service --port PORT --device-id ID inspect --section status
```

Omit `--after-command-id` for the first journal page; map it to null. CLI `clear-entry` maps to serial section `clear_entry`; other hyphenated command names map to the corresponding dotted table name. `operation-get` maps to `operation.get`; `fw-provision` validates `file_version` and sends `provision.set`. Every args file and operation file is protected as above. The shell tokens PORT/ID and all uppercase IDs are placeholders, not inferred devices or safe motor values.

Normal maintenance is stop → service-prepare(ordinary) → bounded calibration/reference/position preparation → current locked verification → service-exit → explicit host arm/readiness. Lost host key uses stop with `reason:"lost_host_key"`, checks durable stopped/inhibited readback, then the existing stopped-host key-rotation procedure; no local recovery receipt is invented. Preserve known terminal outcomes and unresolved history through rotation/restart/new login.

Unresolved release is host Begin/readback → recovery-enter → inspect exact command → reboot → current recovery welcome → bounded restoration/reference → recovery-seal → inspect/compare seal on host → fresh exact sequenced network query → host Close/readback → recovery-attest-disposition. If preparation must restart, commit the expected-generation replacement on the host first, then recovery-attest-replacement and the new reboot/preparation/seal sequence. Reset may occur while disposition acknowledgement is pending, but motion remains frozen. For another game, complete acknowledgement, establish the final new welcome, service-prepare, reference/locked verification, service-exit, host arm and readiness. The old intent is never resent.

History clearing is separate: stop/history-clear → inspect clear authorization → reboot and explicitly establish a different host session → history-fence → service-prepare(clear) → fresh reference/locked verification → service-exit → host arm/readiness. A lost acknowledgement uses operation-get and state inspection at the same operation identity, never a new clear or motion request.
