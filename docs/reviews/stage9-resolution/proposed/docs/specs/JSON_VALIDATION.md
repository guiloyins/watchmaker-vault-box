# JSON parsing, validation and independently runnable foundations

This contract defines the JSON implementation and test-stage boundaries. Protocol v1, its schema, supplied fixtures, acceptance IDs and D1–D6 remain authoritative. Library documentation supports the selected APIs; tested compatibility and milestone results belong in [the status file](../implementation-status.md).

## Selected mechanisms

Use Erlang/OTP's maintained `:json` parser from Elixir through `Vault.JSON`. Require OTP 27 or newer; lock the actually tested OTP/Elixir combination in M0. Call `:json.decode/3` with explicit callbacks for object accumulation, strings, integer tokens, float tokens and null. The callbacks preserve duplicate keys until checked and preserve numeric lexemes without binary floating-point conversion. OTP documents these callbacks, returned trailing input and invalid-UTF-8 errors. [OTP JSON API](https://www.erlang.org/doc/apps/stdlib/json.html#decode/3)

Use **yyjson** for the portable C++ core, compiling the same vendored C source for native tests and ESP-IDF. Its C interface is called only by `vault::json`; it needs no C++ exceptions, RTTI or target-specific parser. yyjson supports UTF-8 validation, ordered duplicate members, explicit input lengths and raw numeric values. Iterate members before field lookup: the parser itself permits duplicates. [Upstream project](https://github.com/ibireme/yyjson)

Keep **Jason** as the Phoenix/framework JSON codec, explicitly declared and locked in `server/mix.exs`/`mix.lock`; retain `config :phoenix, :json_library, Jason`. Framework-generated LiveView traffic keeps the framework codec. `Vault.JSON` is not a drop-in Phoenix codec, and raw device messages, durable JSON and local service data do not use Jason's default map/float decode. Browser hook payloads are already framework-decoded terms and still require their separate strict actor/action validation. [Jason API](https://hexdocs.pm/jason/Jason.html)

Implement hand-written version-one structural validators in both languages. They implement the accepted schema's finite set of branches, required fields, types, enums, numeric/string/array constraints and conditionals. Do not add a runtime JSON Schema engine, code generator, Decimal dependency or schema library to either runtime. The existing Python `jsonschema` dependency remains a development-only independent oracle. Source schema remains the authority; schema changes require synchronized validators and tests rather than an ignored schema version.

## Shared decoding boundary

`Vault.JSON.decode(bytes, %{max_bytes: b, max_depth: d})` returns `{:ok, parsed}` or `{:error, reason}`. The limits are caller-owned constants, never received JSON values. `vault::json::decode` takes the equivalent limits and an exclusively owned workspace; it returns a typed result and borrowed parse tree valid only until that workspace is reset. Complete validation and copy approved typed fields before releasing it. No parsed pointer enters a queue, durable record or command cache.

The wrapper's parsed form has string keys, strings, arrays, objects, booleans, null and private exact-number tokens. Elixir maps null to `nil`, strings/keys to binaries, arrays to lists and duplicate-free objects to maps. Both numeric callbacks return private `{:json_number, lexeme}` tokens. Booleans stay booleans. C++ uses yyjson raw values plus length-aware strings. Only validators convert approved numbers to Elixir integers or `uint64_t`; no private numeric token reaches a domain/model operation. Fixed enum matching may produce existing atom/enum literals; never convert incoming text to atoms.

Apply these stages in order:

1. Assemble within the transport's byte cap before parsing. A single pass with string/escape tracking counts `{`/`[` container depth outside strings; the root container counts as one, scalar values add zero. Reject depth above the selected limit before entering the general parser. This preflight is a resource guard; the selected library still validates the complete JSON grammar.
2. Parse exactly one UTF-8 JSON value. Reject malformed escapes, invalid UTF-8, lone surrogate escapes, comments, trailing commas, BOM, NaN/Infinity, unescaped control bytes and non-whitespace trailing content. A complete WebSocket message must have an object root. The USB framer removes exactly its specified delimiter before invoking the same object parser. A raw NUL byte is invalid JSON; an escaped `\u0000` inside a generic string remains length-aware data unless that field's own grammar forbids it.
3. Reject duplicate **decoded** member names at every object depth, including ignored extensions and escape-equivalent names such as `"type"` and `"\u0074ype"`. Compare decoded UTF-8 bytes without Unicode normalization. OTP's object callback checks before map insertion. C++ sorts member-key references within bounded scratch space and rejects equal adjacent decoded keys; reuse this scratch for each object rather than allocating per object.
4. Apply the format's structural validator and return its normalized allowlisted value. Missing and explicit-null are distinct. Unknown fields are ignored only where that format permits them. All data still passes syntax, duplicate, byte and depth checks even when its fields are subsequently ignored.

For yyjson, call `yyjson_read_opts` with **only** `YYJSON_READ_INSITU | YYJSON_READ_NUMBER_AS_RAW`, an explicit length and a fixed pool from `yyjson_alc_pool_init`; do not enable stop-when-done, relaxed syntax or invalid-Unicode flags. Reserve the documented input padding. Size the parse pool using `yyjson_read_max_memory_usage(b, flags)` from the pinned source and check for overflow/zero; never use the dynamic allocator or fallback heap growth. Allocation failure is a bounded failure, not a partially accepted object. Its documentation describes the allocator ownership and error result. [yyjson API](https://raw.githubusercontent.com/ibireme/yyjson/master/doc/API.md)

Allocate the firmware parser workspace once per owner, outside task stacks, and serialize network/service parsing through that owner. For the inspected source, in-situ read storage is `12*b+256` bytes: 98,560 bytes for an 8,192-byte document, plus input/padding and a reusable key-reference array bounded by the input size. Use `floor(b/5)+1` key slots (a conservative upper bound from JSON member syntax), with checked size arithmetic. Do not silently reduce the 8,192-byte wire limit to fit a target. Verify the selected target's required heap/stack headroom and parsing latency with this workspace and its actual TLS/display stack before target acceptance. The source-computed allocation bound is not target memory evidence. [yyjson header](https://raw.githubusercontent.com/ibireme/yyjson/master/src/yyjson.h)

Use separate profiles: wire device-to-server 4,096 bytes/depth 8; server-to-device 8,192/depth 8; checkpoint 8,192/depth 8; bounded simulator durable JSON 524,288/depth 12. The last profile is server-only and is never allocated on ESP32. Local USB service owns its independently specified request/response caps and field rules. Source schema/fixture readers use an explicit development-only 262,144-byte/depth-64 profile, never selected by a network/service caller. The generic decoder supplies no permissions, credential scope or state transitions.

Normalize errors to fixed categories `size`, `depth`, `syntax`, `utf8`, `duplicate_key`, `root_type`, `shape`, `number` and `resource`, optionally with a bounded numeric offset. Do not log the input, offending value, credentials, library exception or raw error text. A wrapper error produces no domain call and does not consume a discrete command sequence. Device adapters apply their existing protocol-close behavior; USB and durable-store adapters apply their own documented error/fail-closed behavior. These categories are internal and introduce no new v1 response fields or codes.

## Exact integer semantics

JSON Schema's `integer` means a mathematical integer, independent of token spelling. Accept `1`, `1.0`, `1e0` and `10e-1` where the field allows one; reject `true`, `"1"`, fractions and out-of-range values. This is existing schema semantics, not an extension. [JSON Schema numeric reference](https://json-schema.org/understanding-json-schema/reference/numeric)

Implement `Vault.JSON.Number.integer(token, min, max)` in `server/lib/vault/json/number.ex` and the equivalent helper in `firmware/components/vault_json/json_number.cpp`. The parser validates number grammar; the helper analyzes sign, coefficient digits, decimal position and exponent text. Strip insignificant leading/trailing coefficient zeros while accounting for scale; zero, including negative zero and zero with an enormous exponent, normalizes to zero. A nonzero negative value fails unsigned fields. Check whether a negative final scale leaves any nonzero fractional digits. Compare the resulting integral digit count and decimal digits against bounds **before** constructing the integer. Parse exponent digits with saturation relative to the bounded token length and the 16-digit safe-integer ceiling; never expand powers of ten, allocate exponent-sized buffers or convert through `double`/BEAM float. This handles cancellation such as a long coefficient followed by a negative exponent in linear bounded work.

All v1 integer fields use their exact schema minima/maxima, with 9,007,199,254,740,991 as the maximum safe integer. The `const` numbers use the same exact comparison; no language's `true == 1` shortcut is permitted. `9007199254740990.5` is nonintegral and rejected; `9007199254740991.0` is accepted when that field allows the maximum; `9007199254740992` is rejected. Valid unknown extension numbers remain raw tokens for complete decoded-message comparison and are omitted from routed domain values; an extension such as `1e999999` is not rounded, expanded or used as a domain integer. The raw-number implementation takes its lexical path before floating conversion. [yyjson numeric source](https://raw.githubusercontent.com/ibireme/yyjson/master/src/yyjson.c)

`Vault.Protocol.V1.validate(parsed)` and `vault::protocol::validate_v1(parsed)` implement these schema groups. Their shared-schema hash is recorded with the validator coverage table; a changed schema hash requires review of the table and both validators.

| Schema group | Required implementation |
| --- | --- |
| Scalars | `$defs/id`, `text`, `seq`, `version`, `role`, `phase`, `rune`, `release_status`, `position`, `position_basis`, `failure`: exact enum/null/range rules. IDs are 1–64 ASCII characters matching `[A-Za-z0-9_-]+`. Text length is Unicode scalar count, not UTF-8 bytes or grapheme clusters; default other-string cap is 128, including bounded extensions unless a format explicitly supplies another cap. |
| Arrays | `roles`, `pause_reasons`, `peers`, maze walls/moves: exact cardinality, element types and schema-defined uniqueness. Do not invent `uniqueItems` for peers; role ownership/participant consistency stays domain validation. |
| Hello/welcome | Discriminate hello by `device_class`, validate its capabilities, welcome's null assignment, role arrays and exact 100/400/1500 constants. Both capability definitions explicitly permit additional properties; preserve that exception. Unknown capabilities never grant authority. |
| Commands/results | Five `command` action branches, each required context and exact payload; each `command_result` code's status and exact data object, including empty-data branches. No fallback branch for a new action/result code. |
| Snapshots | Three projection branches; public/box forbid `maze`, `seal`, `hold`, `board_version` even when null. Controller phase, pause and A/B role conditionals must all be checked, including move ordering and partner clue role. |
| Nested DTOs | Exact maze/seal/hold/readiness/box/peer/confirmation keys; armed-readiness conditional, simulated-confirmation prohibition and historical confirmation iff `position_confirmed`. Do not conflate current position with historical confirmation. |
| Heartbeats | Request/sample/ack fields, nullable input and pressed/press-ID conditional. Acknowledgement `code` does not invent schema conditions absent from the accepted schema; stateful acceptance remains the domain owner's work. |
| Box messages | Arm/disarm/command/query/feedback shapes, status's null-command-session conditional and confirmation conditional, status-ack accepted/code relation, feedback 0–100 and 100–1500 ranges. |

Top-level extensions remain allowed, as do the two capability-object extension locations. Strict nested payloads/readiness/projections and explicitly forbidden public/box properties remain strict. Unknown extension subtrees have no invented v1 property allowlist; they still consume byte/depth/string resources. Route only normalized schema-known fields to domain operations, but retain the complete decoded comparison value described below for command/status retry caches, including every permitted extension member. A changed extension value under a reused sequence is changed content and must be rejected. Structural success alone does not establish authorization, direction/class binding, sequence validity, ownership, freshness, fixture-correct walls/clues or physical readiness; those checks remain at the existing domain/adapter boundaries.

### Complete decoded-message retry comparison

`Vault.JSON.comparison(parsed, max_bytes)` and `vault::json::comparison` produce an owned, bounded comparison byte string from the complete successfully parsed object **before** dropping extension fields. Command/status windows retain it with the existing result/ack, preserving the protocol's 128-command and 16-status cache limits. Compare these byte strings directly; a digest alone is not the retained decoded value. This changes neither sequence consumption/rejection rules nor the separate durable box-command fingerprint of original session/action/target. Permitted extensions affect equality of retry content, but never grant capability, authority or a routed operation.

The comparison format is an internal typed encoding, separate from JSON wire bytes and the integer-only canonical durable/request codec. Its tags are one ASCII byte: `n` for null, `t`/`f` for booleans, `s` for strings, `a` for arrays, `o` for objects and `d` for numbers. Every length/count uses unsigned minimal ULEB128. A string is `s`, byte length, decoded UTF-8 bytes. An array is `a`, element count, then values in original order. An object is `o`, member count, then key/value pairs sorted by decoded key UTF-8 bytes; keys use the string encoding. This supports non-ASCII extension keys, treats object member order as immaterial, preserves array order and distinguishes strings, numbers, booleans and null. Decoded string bytes are compared exactly with no Unicode normalization; whitespace and equivalent JSON escapes are immaterial. Duplicate decoded keys have already been rejected.

A number is `d`, sign byte (`0` nonnegative or `1` negative), coefficient byte length, coefficient ASCII digits, exponent sign byte, exponent byte length, exponent ASCII digits. It represents `sign * coefficient * 10^exponent`; signs are binary bytes, not ASCII digits. Remove leading coefficient zeros and remove trailing coefficient zeros while increasing the decimal exponent; subtract the original fractional-digit count from the token exponent. Nonzero coefficients have no leading/trailing zeros. Exponent magnitude has no leading zeros; zero exponent is nonnegative `"0"`. Every numeric zero, including negative zero, has nonnegative coefficient `"0"` and exponent `"0"`. Thus `1`, `1.0`, `10e-1` and `1e0` compare equally, while `1.5` and `1.5001` remain distinct. Known integer fields may use their already validated mathematical integer value to build this same representation.

For arbitrary extension numbers, preserve the exact exponent as signed decimal digits and perform only bounded digit-string addition/subtraction of the fractional-digit/trailing-zero counts. Do not use the integer validator's saturating exponent as the comparison exponent: that would collapse distinct huge numbers. Do not convert to floating point, expand a power of ten, or impose a safe-integer restriction on a number in an unrestricted extension position. `1e999999` and `10e999998` compare equally, and `1e999999` and `1e999998` differ, with storage/work proportional to their bounded input text.

Build the comparison into at most `8 * max_bytes + 64` bytes, with checked arithmetic and no unbounded fallback; this conservative allowance covers the typed tags/lengths and normalized coefficient/exponent digits for any message under the existing byte cap. A resource failure yields no domain action or sequence consumption. Retain only the owned comparison bytes, never yyjson workspace pointers. Tests cover the worst token density and exact bound, object reordering/escape equivalence, arrays, changed extension keys/values and exact huge-exponent equality/difference through both retry windows. The durable canonical encoder is never used to compare arbitrary extension numbers.

## Canonical durable/request encoding

`Vault.JSON.canonical/1` and `vault::json::canonical` accept **already structurally validated** JSON-domain data with ASCII object keys and integer-only numbers. They return bytes or an explicit error and never hash unvalidated input. Recursively sort keys by ASCII byte order, preserve array order, use decimal integers without leading zeros/exponents and normalize zero. Encode null/booleans as `null`/`true`/`false`. Escape quote and backslash, use the short escapes `\b`, `\t`, `\n`, `\f`, `\r`, and encode other U+0000–U+001F controls as lowercase `\u00xx`. Emit other Unicode scalars as their original UTF-8 bytes; do not normalize Unicode or escape `/`. Emit no insignificant whitespace. Reject floats, raw-number tags, duplicate/non-ASCII object keys and unsupported runtime structs.

This format defines semantic request/checkpoint digests within this project; it is not a claim of RFC 8785 compliance or a new network signature. Callers hash the returned bytes with SHA-256 using OTP `:crypto` or the firmware's cryptographic provider and specify their exact included fields separately. Pure canonical encoding starts no application. Normal wire encoders build schema-known typed objects, serialize with OTP `:json.encode/2` or yyjson and verify encoded size before queue admission; numeric outputs use normalized integer values. The OTP wrapper explicitly encodes Elixir `nil` as JSON `null`; it never relies on OTP's default arbitrary-atom encoding. Only true/false/nil are permitted scalar atoms and all object keys are binaries. Firmware outbound mutable-document and writer allocations use a separate bounded scratch reservation, checked failures and no dynamic fallback; release receive scratch before encoding queued typed responses.
