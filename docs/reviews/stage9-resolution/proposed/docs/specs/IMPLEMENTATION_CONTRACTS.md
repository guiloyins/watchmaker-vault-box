# Internal interfaces and durable state, version 1

This document fixes the internal interfaces used by the M0 pure model and M1/M2 consumers. It implements the accepted game, recovery and maintenance rules; it adds no network-v1 message, field, capability or release status. [Protocol v1](PROTOCOL_V1.md) remains the wire authority. Local operator exchanges use [Local service v1](LOCAL_SERVICE_V1.md); JSON parsing and canonical encoding use [JSON validation](JSON_VALIDATION.md) and `Vault.JSON`. The structures below are strict: all listed keys are required, nullable fields are explicit, and other keys are rejected. Host-only records never enter participant or box projections.

## Common values and ownership

`ID` is 1–64 ASCII characters matching `[A-Za-z0-9_-]+`; newly generated opaque IDs contain 128 random bits (the internal deterministic store-operation IDs below are the sole exception), encoded as 32 lowercase hexadecimal characters with an optional descriptive prefix. Device IDs remain their provisioned stable IDs. `N` is an integer in 0–9,007,199,254,740,991; `P` is the same range starting at 1. Overflow faults visibly instead of wrapping. `Role` is `a|b` for the present puzzle; protocol C/D values grant no current permission. `Rune` is `star|moon|sun|wave`. `AuditMs` is a nonnegative UTC Unix millisecond integer and is never a freshness deadline. Runtime `MonoMs` may be negative and belongs to one VM/clock instance only. Hashes are SHA-256: 32-byte BLOBs in SQL, 64 lowercase hexadecimal characters in JSON. Hashes detect equality/corruption, not operator authenticity.

Use fixed Elixir atoms only after explicit allowlist conversion. External JSON has string keys and JSON null; typed Elixir structures use `nil`. Durable documents contain no Erlang term serialization, process reference, secret, live lease or reusable connection authority. Canonical JSON uses the algorithm in `JSON_VALIDATION.md`; request hashes cover the validated normalized operation, including its operation kind, principal credential ID, game and expected context, but excluding transport delivery metadata. Digest equality never permits bypassing current read authorization.

The GameSession is the sole writer/coordinator for a loaded game's checkpoint, release observations and administrative transactions. BoxLink submits observations through it and does not replace command rows. Stopped setup/credential tasks use the existing maintenance guard. Their host-key mutation never participates in gameplay or win transactions.

`Receipt` exact fields are `request_id, operation, game_id, session_id, state_revision, data`; these are internal browser/admin results, not device envelopes. Host operation rejections use fixed codes `not_authorized|not_found|stale_session|wrong_phase|not_ready|unresolved_release|recovery_exists|recovery_replaced|already_closed|evidence_stale|evidence_mismatch|request_conflict|storage_error|readback_required`; `data` is empty except authorized host readback identifiers/current revisions. Bind failures additionally use `invalid_binding`. Controller protocol errors retain the existing v1 vocabulary.

Commands have exactly the v1 128-result connection window and 500 ms/three-identical-retry policy. A stored durable transition is not permission to reconstruct a command on another connection. Browser host requests retain a random request ID until their result/readback is known. Same ID plus equal normalized arguments returns the original result; changed arguments return `request_conflict`. A transient admission/storage failure with no committed receipt may be explicitly retried with that ID and the same expected context; an ambiguous commit must first be read back. Rejections that are part of a committed operation receipt remain rejections on retry. New IDs are required for new user decisions.

## Browser hook boundary

The LiveView adapter derives the Actor from the mounted authenticated process; a received actor ID is only a lookup/check, never authority. Hook JSON objects are strict and limited to 2,048 bytes inbound, 8,192 bytes outbound, depth eight, the common ID/integer limits and at most the v1 30 samples/commands per second with burst ten per actor. No browser event accepts a timestamp as freshness evidence.

| Event | Exact payload |
| --- | --- |
| Server `vault:rebind` | `{actor_id,boot_id,connection_id,binding_generation,session_id,round_id,puzzle_revision,role,control_epoch,required_roles,allowed_roles}`. Nullable role/epoch. Delivered only after adapter authorization; clears pending input/results and local contacts; resets counters only when connection_id changes. It precedes the explicit bootstrap snapshot. |
| Server `vault:challenge` | `{actor_id,connection_id,binding_generation,heartbeat_seq}`. The issue time remains server-side. |
| Client `vault:input` | `{actor_id,connection_id,binding_generation,heartbeat_seq,input_seq,input}`; `input` is exactly the v1 nested input object or null. Complete neutral samples remain valid while paused. |
| Client `vault:command` | `{actor_id,binding_generation,command}`; `command` is the exact validated v1 command object. This reuse defines browser data, not a raw WebSocket on LiveView. |
| Server `vault:input_result` | `{actor_id,binding_generation,heartbeat_seq,input_seq,input_accepted,code}`. |
| Server `vault:command_result` | `{actor_id,binding_generation,result}`; `result` is the exact v1 command_result object. It cannot overwrite a newer snapshot/grant. |
| Server `vault:invalidate` | `{actor_id,connection_id,binding_generation,reason}` where reason is `paused\|resumed\|role_changed\|session_changed\|disconnected\|expired\|logout`; clear local contacts/pending actions and wait for current context. |

Example released sample: `{"actor_id":"actor_a","connection_id":"conn_a","binding_generation":2,"heartbeat_seq":7,"input_seq":9,"input":{"session_id":"session_2","round_id":1,"puzzle_revision":1,"role":"a","control_epoch":4,"pressed":false,"press_id":null}}`.

Session or scope changes fence queued snapshots as well as these events. A role/epoch change on the same connection updates context through `vault:rebind` but does not reset connection-wide command/input/heartbeat sequence counters; only a new connection does. A new hook boot resets press numbering; a rebind within the same boot retains its greatest press ID and demands neutral then a strictly greater press. Rebind includes no synthetic press. The client requires actual lift before its neutral baseline can unlock a new contact. Local clear paths and host A/B key mappings remain exactly as specified.

## Recovery identity and evidence

An intent's immutable identity is `{game_id, command_id, intended_box_id, original_session_id, original_round_id, fingerprint}`. Fingerprint is exactly `{session_id: original_session_id, action: "set_latch", target: "released"}`. Round identity is server evidence, not a new wire fingerprint field.

`PreparationReceipt` has exactly `request_id,recovery_id,recovery_generation,current_session_id,game_id,command_id,intended_box_id,original_session_id,original_round_id,fingerprint,prior_recovery_id,committed_at_ms`. `prior_recovery_id` is null for Begin and the replaced ID otherwise. `recovery_generation` starts at 1 and increases exactly once for a successful replacement. GameSession restart changes the current game session, not the original preparation receipt or recovery identity. The host shows current binding separately; no receipt claims continued live authority. `read_operation.current` is the current committed host context for local resealing after restart; zero recovery_generation accompanies nil recovery_id. The local seal request carries an operator-attested `{session_id,recovery_id,recovery_generation,disposition_id}` from that current context and the actual current welcome. It may refresh the same recovery record's session binding without replacing the historical preparation receipt, clearing freeze or changing generation.

`CloseEvidence` has exactly `local_record_id,service_epoch,seal_operation_id,recovery_id,recovery_generation,box_boot_id,connection_id,current_session_id,status_seq,observation_id,query_id,operator_confirmed`. The first three values and seal context are transcribed from the sealed local record; `operator_confirmed` must be true. The observation/query IDs and binding/status values must equal server-selected evidence, not arbitrary client facts. The local record follows `LOCAL_SERVICE_V1.md` §6 and includes the matching original identity, reboot and current sealed context. Service epoch is P; local record/seal/query/observation IDs are ID.

`DispositionReceipt` has exactly `request_id,disposition_id,disposition,game_id,command_id,intended_box_id,original_session_id,original_round_id,fingerprint,recovery_id,recovery_generation,closed_session_id,local_record_id,service_epoch,seal_operation_id,box_boot_id,connection_id,status_seq,committed_at_ms`; `disposition` is always `closed_no_replay`. The host stores the complete evidence and reason separately. Local acknowledgement records this receipt's identity, never rewrites a command's execution result, and is an operator attestation rather than cryptographic proof.

## Server SQLite/Ecto schema version 1

The tables below are exhaustive application tables; Ecto's standard `schema_migrations` bookkeeping is additional. Set server pool size 1, WAL, `synchronous: :full`, `foreign_keys: :on`, `busy_timeout: 100` and write transactions `mode: :immediate`; verify effective settings on every connection. No network/service wait occurs inside a transaction. The mode and timeout are proposed configuration, not measured guarantees.

SQL/Ecto mappings: `ID = TEXT/:string`, `TEXT = TEXT/:string`, `N/P/AuditMs = INTEGER/:integer`, `BOOL = INTEGER/:boolean` with CHECK in `(0,1)`, `HASH = BLOB/:binary` with length 32, `JSON(n) = TEXT/:string` with encoded UTF-8 byte length <=n. JSON columns use a bounded codec, not Ecto's implicit map/array representation. Every integer has `typeof(column)='integer'` and its range CHECK; text/blob type and length checks are explicit. IDs also have explicit `length(CAST(column AS BLOB)) BETWEEN 1 AND 64`, `instr(column,char(0))=0` and `column NOT GLOB '*[^A-Za-z0-9_-]*'` CHECKs. All columns are NOT NULL with **no SQL default**, except `?` means nullable/default NULL and `=value` names an explicit default. All PKs are explicitly NOT NULL. Foreign keys have `ON DELETE RESTRICT ON UPDATE RESTRICT`, never cascade; create an index on each child FK unless an indicated primary/unique index already has it as a leading key. Each such single-column child index is named `idx_<table>_<column>`; this naming rule fixes the complete remaining index set. Cross-table logical checks run in GameStore transactions and on load.

The exact-report key deliberately permits different payloads at the same status sequence, so a contradiction cannot destroy the original.

Triggers reject UPDATE/DELETE of observation, preparation, disposition and operation rows, and DELETE of actuator commands. A command UPDATE may change only `dispatch_claimed` 0→1, `dispatch_retired` 0→1 with nonnull retirement time, and `history_revision` N→N+1. CHECK requires retired_at_ms null iff dispatch_retired=0. Retirement time cannot change after set; no other command column changes. Store metadata IDs and version are immutable outside an explicit migration. Game identity is immutable; checkpoint writes require revision CAS. These rules retain original solve identities and closure receipts permanently, independently of optional diagnostic pruning. Desired assignments can change, and enabled/epoch/digest changes obey the existing stopped-maintenance rules.

`request_id` in preparation/disposition also references `game_operations.request_id`; implement these as initially deferred FKs in the migration and insert both rows within the same transaction, with all receipt values allocated before insertion. Recovery prior rows must share command and have generation exactly previous+1. Disposition recovery, observation and command must match. Validate these cross-row conditions transactionally and reject inconsistent startup state. No per-connection status cache is a durable source of authority.

### Checkpoint encoding

The exact schema-1 JSON fields are `schema_version:1,game_id,session_id,round_id,puzzle_revision,state_revision,phase,position,board_version,selected_runes,paused,pause_reasons,required_roles,active_time_ms,release_command_id`. Integers obey common limits; position0..15; phase is the four specified phases; selected_runes is exactly `{a: Rune|null,b: Rune|null}`; pause_reasons is a unique subset of the four v1 reasons; required_roles is exactly `["a","b"]`; release_command_id is ID|null. `schema_version` and game_id must equal the row. Limit is8,192 UTF-8 bytes/depth8. Lobby initialization: round1, puzzle_revision1, position12, board/state revisions0, both selections null, paused false, reasons[], required A/B, active_time0, release null.

Unpaused checkpoints have no pause reasons; paused checkpoints have at least one. Seal/solved position is3. Solved iff release_command_id is nonnull, and that row belongs to this game and original attempt. After recovery, current session may differ from its intent's original session; never rewrite the latter. Reset creates a new session, round1 and lobby checkpoint while leaving old command records. State revision resets to0 only with a new session; checkpoint_revision always increases across sessions. The server adds elapsed active monotonic time only at durable transitions; a crash can lose the final uncommitted elapsed interval, which has no puzzle effect. Holds, pressed state, credentials, diagnostic lists, release observations, arms and current physical facts are absent.

### Transaction predicates and readback

Each operation uses `BEGIN IMMEDIATE`, exact request-hash readback first, checkpoint revision/session CAS where applicable, and all writes/receipt in one commit. A request with a matching stored receipt returns it after current authorization even if its expected old session is no longer current. Same ID/different hash is `request_conflict`. No stored result grants live authority or repeats an effect. Transactions test all predicates again after acquiring the writer; failed predicates roll back and cause no receipt/effect. After any wait, qualification rechecks current monotonic deadlines and ordinary actor validity before committing. No rotation epoch race is added.

| Operation | Required predicate and atomic writes |
| --- | --- |
| Ordinary checkpoint | Expected checkpoint_revision/current session; action legal against current state. Update the checkpoint CAS and operation receipt; explicit host assignment/replacement also updates its desired assignment row atomically. It never touches historical observation rows. Adopt/publish only after commit. |
| Win | Current unpaused seal, still-current qualification token/role owners/press IDs/selections; every lease strictly fresh and overlap>=2000ms; current configured box armed/ready with fresh accepted heartbeat. Insert command under one-solve unique key, solved checkpoint referencing it and operation receipt. Capture original dispatch binding `{box_boot_id,connection_id,session_id,arm_id,heartbeat_seq,binding_generation}`. If uniqueness already exists, load its original result; never mint another ID. |
| Initial dispatch claim | Only the current owner holding the postcommit volatile win ticket may CAS `dispatch_claimed=0 AND dispatch_retired=0` to1 for that exact immutable binding and current session. Emit once after successful claim and a final current-binding/retirement check; no reconstructed ticket on restart/readback. Ambiguous claim/send becomes query-only. A recovered unclaimed row is also query-only. |
| Begin | Current solved checkpoint references command, no preparation/disposition exists, authenticated host and expected session match. Insert generation1/recovery ID with prior null, set retirement once, rotate current session to a new paused recovery checkpoint, and insert receipt. Fence actors/arms/queued effects after commit and before acknowledging. |
| Replacement | Same original command; latest preparation equals expected_recovery_id and no disposition exists; current expected session/host valid. Insert next generation with prior link, keep retirement, rotate paused session and receipt. Close and replacement obtain the same SQLite writer lock; only one can satisfy predicates. |
| Close | Latest preparation equals expected recovery; no disposition exists; retired original command and solved checkpoint still match. Explicit host confirmation/reason and same local sealed identity/reboot/service epoch. Current intended box is authenticated in exact boot/connection/session; current arm nil, motor inactive, fresh heartbeat lease; server-recorded exact-command query observation matches evidence, has seq greater than query's pre-send floor, and was received after the query was sent after seal attestation. No later admitted contradictory current-state observation may exist. Insert disposition and receipt only; leave all reported outcomes unchanged. |
| Reset | An unsolved game with no release intent uses ordinary host Reset. For a solved game with no preparation: known terminal outcome and current idle mechanism. With any preparation: matching durable closed_no_replay and stopped/disarmed recovery evidence, regardless of a later terminal report. Create new session/lobby; preserve all history/retirement. Local acknowledgement may remain pending but motion freeze continues; Reset supplies no arm. |
| Status observation | Append a new exact report or read its existing row; increment command history_revision only for a new row. Null-command readiness has no command write. Wrong identity/changed duplicates are retained as classified conflicts but cannot authorize readiness or closure. Then acknowledge/apply only permitted current state. |

Current query binding and monotonic receipt times are volatile, maintained by the serialized GameSession. The observation row is historical evidence, not a reusable Close authorization. A restart, disconnect or binding change invalidates closing evidence, even if a sealed receipt or identical query row remains in SQL. Within one connection, only one exact-command query is outstanding; the adapter allocates query_id locally and annotates an eligible newer reply without adding a wire field. This association and the operator attestation do not claim instantaneous knowledge of remote state.

Reduce historical status from all retained admitted observations, not last-write-wins. `accepted` followed by terminal completion is progression; a later stale duplicate is not reversal. An unknown-current-journal observation after acceptance, interrupted outcome, incompatible terminal outcomes or conflicting confirmation creates retained uncertainty. Later readiness or administrative closure cannot promote that uncertainty into historical certainty. Preserve each original reported value, including any prior command_confirmation. Contradictory current armed/moving evidence blocks Close; a late contradictory observation after an already committed Close is appended and displayed, never deletes the disposition or restores delivery. A transaction writing a checkpoint or disposition never copies/replaces an observations list.

On known rollback retain the last checkpoint and enter volatile storage-error recovery pause. On lost commit reply, stop effects, query `game_operations` using the same request ID and compare its hash/revision; if unavailable, stay paused/quarantined. Readback adopts committed puzzle/history only, clears live input, and never dispatches an old win/arm. Arm receipts record a request decision, not proof of remote arming; a missing/readback reply requires a fresh status query. Failed or ambiguous observation persistence gets no accepted status acknowledgement; do not discard the report before bounded retry/disconnection handling. Unavailable original server history never invokes empty initialization.

## Simulated durable singleton schema

One independently owned SQLite file/connection per instance contains `box_state`: `singleton INTEGER PRIMARY KEY NOT NULL CHECK(singleton=1)`, `schema_version INTEGER NOT NULL CHECK=1`, `instance_id TEXT NOT NULL UNIQUE`, `device_id TEXT NOT NULL`, `revision INTEGER NOT NULL CHECK>=0`, `last_operation_id TEXT NOT NULL`, `payload_sha256 BLOB NOT NULL CHECK length=32`, `payload_json TEXT NOT NULL CHECK length(CAST(payload_json AS BLOB))<=524288`. Apply the same type/range/ID checks and WAL/FULL/100ms settings as the server. `PRAGMA user_version=1` plus payload schema/version must agree. The schema has no FK to GameStore and cannot share its file. `Store.init_new(path, instance_id, device_id)` is exclusive explicit creation; `Store.open_existing(path, expected_instance_id, expected_device_id)` never creates.

The strict payload root has exactly `schema_version:1,instance_id,device_id,store_revision,last_operation_id,journal,service,reconciliations,absent_reconciliation,clear_authorization,service_receipts,simulator_configuration`. Limit524,288 UTF-8 bytes/depth12. Fields match row identity/revision/hash. Model journal subrecords carry `schema_version:1`; LOCAL_SERVICE_V1 subrecords retain its exact `storage_version:1` field; required missing/null/version-mismatched records fail closed. Root metadata excluding arrays/subrecords<=16,384 bytes. It stores no credentials or live calibration/start verification; independent provision/calibration configuration is neither erased nor recreated by history clearing.

A full reachable state reserves 32×2,048 journal bytes +33×4,096 reconciliation bytes +64×3,072 receipt bytes +98,304 clear-authorization bytes +16,384 bytes for root keys, delimiters and service control =512,000 bytes, below524,288; service control and simulator configuration (each<=4,096) are included in the16,384 remainder. This deliberately budgets both pre-erase records and their complete clear copy simultaneously; validate both individual and total encoded lengths before accepting a mutation. A capacity/size error returns a fixed refusal and never evicts accepted journal entries or authorizing evidence. The simulator's file/JSON limit is a host storage choice, not a declaration of physical NVS capacity; physical record allocation must satisfy the separate local-service/firmware contract. Firmware does not decode or store this whole512KiB JSON singleton: it uses its versioned typed NVS records and unchanged bounded serial/network frames. Shared semantics do not require shared storage encoding.

`Store.commit(handle, Persist)` transaction reads current identity/revision/hash, validates the legal patch against that document, and performs `UPDATE ... WHERE instance_id=? AND revision=? AND payload_sha256=?`; exactly one affected row is required. Write next revision/last_operation_id/payload/hash atomically. After lost reply, read row: exact operation/revision/hash means committed; unchanged base revision/hash means not committed; any other state is conflict/quarantine, not permission to overwrite. Readback never claims that motor movement did or did not occur. `ReadExpectation` is exactly `{instance_id,operation_id,base_revision,next_revision,expected_sha256,payload_sha256}`, copied from the pending Persist before issuing its write. `Store.readback(handle, ReadExpectation)` returns exactly `{:committed, revision, payload_sha256, durable}`, `{:not_committed, revision, payload_sha256}`, or `{:error, :conflict|:unavailable|:invalid_store}` by those predicates. Readback therefore has both expected hashes and revisions, rather than inferring noncommit from an operation ID alone. If a runtime restart lost that pending expectation, open_existing validates the actual durable document and follows inactive boot reconciliation; it never manufactures a not_committed result or an executable effect. The adapter serializes writes and refuses another while uncertain; a stale callback cannot overwrite a newer record. Local service receipts handle evicted retries with a monotonically increasing revision and sequence-bearing ID, returning `receipt_expired` or conflict without execution.

Clearing uses separate committed steps: persist and verify full clear authorization outside journal; erase the named journal/attached reconciliation subset and any included acknowledged absent record, atomically clearing only a matching active_local_record_id pointer; retain clear_operation_id, inhibit/freeze and the complete clear copy; reboot; establish different session; commit fence completion; deliberate authorized unfreeze into preparation; establish fresh modeled reference/locked readiness; deliberately exit service durably; obtain new arm. A crash at any step restores the remaining gates. After erasure, service.prepare(clear) reads its authorization from the retained ClearRecord, not a deleted reconciliation or pointer alias. inspect/recovery never substitutes a clear entry for a missing reconciliation. Do not infer authorization from an empty journal or automatically discard clear evidence on load. GameSession reset never changes this database. Service history clearing never changes the server's permanent command/recovery/disposition/operation history or service revision high-water mark.
