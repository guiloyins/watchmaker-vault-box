# Acceptance and verification plan

This is an executable acceptance contract for the implementation described in `WATCHMAKERS_VAULT_SPEC.md` and `PROTOCOL_V1.md`, incorporating [the supplied hardware update](WATCHMAKERS_VAULT_HARDWARE_UPDATE.md). It does not report tests already performed. Follow M0–M5 in order; independent hardware preparation may proceed alongside software. M1 must remain a usable browser demonstration while hardware verification continues.

Use **Passed, Failed, Blocked, or Not run** for each case. Record whether evidence is unit-tested, simulated, compiled, flashed, or physically observed. A successful compile cannot establish motor behavior; a simulated box cannot establish physical position. Missing hardware blocks only the affected cases.

## M0 — Contracts, environment, and hardware evidence

**M0-01 — Reproducible environment.** From a clean checkout, follow the documented setup commands. Expected: the locked Elixir/OTP, Phoenix dependencies, ESP-IDF revision, selected components, and supported target matrix are identifiable; no unrecorded global configuration is needed. Record actual versions and any unavailable runtime.

**M0-02 — Golden fixture integrity.** Load the private fixture through the pure rules module. Assert 16 connected cells, 15 passages, and the unique route `12,8,9,5,4,0,1,2,6,10,11,7,3`. The branch `9,13,14,15` has no exit shortcut. Assert A’s right-wall indices `[2,5,6,9,12]` and B’s bottom-wall indices `[1,4,10,11]`. Exercise the real initial pure Vault.Projections in M0 for exact role axes, partner clue and own selection; do not require M1 session/runtime or M2 protocol providers. Source schema/fixture validation and byte-for-byte public/private copy consistency are the M0 contract-test scope.

**M0-03 — Evidence before GPIOs.** Produce the board-audit record: exact PCB/chip, display, touch controller, flash/PSRAM, pin sources, driver identification, power arrangement, and antenna placement. Carry forward the supplied ULN2003AN/TI and Freenove 8 RGB LED Module identifications, Rafa's nominal PASCAL internal dimensions, and the observed ESP32-2432S028 dual-USB/CH340C board. Keep the Rv3 ST7789/XPT2046 profile a documented candidate, the second-unit match and exact C5 profile unresolved until supported, and compiled/bench evidence separate from identification. Unknown facts remain explicitly unknown; request specific missing evidence without restarting general photos. An incomplete hardware profile must fail its target build clearly; host fakes and browser work remain available.

**M0-04 — Test seams.** From server/, run `MIX_ENV=test mix test --no-start --only m0 test/vault/puzzle_test.exs test/vault/projections_test.exs test/vault/contract_test.exs test/vault/json_test.exs test/vault/simulated_box/model_test.exs`. All selected :m0 cases exercise real M0 pure providers and require no :vault, Phoenix endpoint, Repo, database, network or hardware; test_helper starts ExUnit only. Confirm no application/runtime resource starts accidentally. Pure model state/event/effect types exist in M0 and literal persistence-completion events require no store. Timing seams control monotonic time/scheduled messages without multi-second sleeps; execute full session/protocol timing and firmware host-fake cases when their later production providers exist. JSON_VALIDATION.md defines exact parser cases, source-only M0 contract scope and isolated M1 pre-start test preparation.

**Gate:** contracts and pure rules are testable; unresolved hardware assumptions are documented and isolated.

## M1 — Playable Phoenix browser game

**M1-01 — One game, multiple views.** Create one game, open separate A/B participant sessions and the host console, then reload each. Expected: one authoritative game process, preserved state, no per-mount game creation, and a clearly labeled simulated box. Start is host-only and requires both controllers plus simulated readiness. Run the in-process adapter against protocol-derived literal conformance expectations; verify its independent runtime and durable store survive a GameSession-only restart. Load the compiled model/store from the locked Mix environment without starting :vault, Phoenix or the server Repo. Assert the fixed principal/actor/API/hook structures and explicit rebind semantics in IMPLEMENTATION_CONTRACTS; independent consumers use the same signatures and result allowlists.

**M1-02 — Correct movement and rejection.** Execute the golden route using the required roles. Each accepted move increments `board_version` once. Wrong-axis, wall, out-of-bounds, paused, and wrong-phase actions preserve position. Entering cell 3 transitions to `seal` without a release command. Held arrows and repeated keydown do not repeat moves.

**M1-03 — Partial information.** Assert exact allowlisted player projections, including their wall orientation, controls, partner clue, and own selection. Inspect initial HTML, LiveView diffs/events, DOM attributes, error replies, source maps, and served assets. None may contain the full maze, route, or hidden expected-answer fields. Rune names themselves are legitimate choices; do not use blanket string-absence assertions.

**M1-04 — Access boundaries.** As an unauthenticated visitor, player A, and read-only observer, attempt host operations, B’s route, forged role parameters, and direct events. Expected: access denied at the server. Changing a URL or hiding/showing a button never grants authority. Join/device secrets do not appear in logs or page content. For generated-key maintenance, race running/starting/stopping applications and separate credential tasks: only one guard owner proceeds and rejected admission performs no credential write. Kill an owner and leave a partial marker; both modes stay blocked without age/PID stealing until every fixture-owned VM/task is stopped and explicit removal permits one new owner. Test protected existing/symlink output rejection, failed writes, interruption before/after durable file creation and database activation, lost commit replies and readback without plaintext/orphan activation. After stop/replace/restart, reject old host keys/cookies, accept the new key, preserve independent credentials/assignments and restore progress paused with cleared live authority. Ordinary expiry/logout still prevents host-held qualification. With terminal and unresolved simulated histories, exercise lost-key local stop/inhibit, stopped replacement, restart/new login and unchanged recovery; preserve original identity/outcome and terminal Reset rules, with no motion, cancellation claim, closure or redelivery from rotation. Physical stopping evidence remains M4 work.

**M1-05 — Host and ownership.** Assign A to a browser actor and B to a simulated device; repeat with assignments reversed. Observer panels remain read-only. Explicit takeover pauses, changes ownership validity, and clears holds. The host’s combined demonstration uses separate A/B actors. Closing a host observer does not pause device-owned players.

**M1-06 — Seal behavior.** Begin with no selections. A sees “Tell B: hold MOON”; B sees “Tell A: hold STAR.” Select A=STAR/B=MOON, then use separate hold controls. Correct overlapping input qualifies once; wrong choices do not expose individual correctness. Selection persists through pause, while held state/progress clears.

**M1-07 — Real browser input lifecycle.** While holding, trigger pointer cancellation, lost capture, blur, hidden tab, navigation, and transport loss. Local feedback clears and server qualification stops. Reconnect/reload requires fresh control context and neutral-then-press input. Test keyboard focus inside forms; game shortcuts must not intercept typing.

**Gate:** two browsers can play the complete game; privacy, ownership, and authoritative completion work before physical devices are required.

## M2 — Protocol, persistence, and deterministic failures

### Timing matrix

Use the injected clock with current session, ownership, correct selections, and a ready simulated box. Keep all unrelated leases fresh unless a case says otherwise.

| ID | Action | Expected result |
|---|---|---|
| M2-T1 | Advance a valid shared hold to 1,999 ms, then 2,000 ms. | No solve before 2,000; exactly one committed solve at qualification. |
| M2-T2 | Issue a challenge at time 0; deliver its response at 399 ms and at 400 ms in separate runs. | First lease ends at 400, not 799; response at expiry is rejected. |
| M2-T3 | Deliver an expired challenge with a larger `input_seq`, then duplicate/reordered samples. | None renews a hold or revives old pressed state. |
| M2-T4 | Stop fresh samples; advance through 400 and 1,500 ms. | Hold clears at lease expiry; silence adds offline/recovery pause at 1,500. Explicit socket close pauses immediately. |
| M2-T5 | Cancel an attempt, then deliver its already-queued completion message twice. | No solve, new command, or progress revival. |
| M2-T6 | Send fresh challenges throughout play without changing visible state. | Heartbeats do not increment board/puzzle/UI revisions or generate full snapshots. |
| M2-T7 | Compare an inactive hold and a newly started hold, both with `elapsed_ms:0`. | `hold.active:false` stays still; `hold.active:true` starts progress. Zero elapsed time must not imply inactivity. Cancellation clears active state. |

**M2-01 — Sequence contract.** Repeat an identical discrete command, reuse its sequence with changed content, send a gap, and request an expired cached result. Assert the documented result codes, one application at most, and bounded 128-result cache. Two moves observing board version N cannot both apply. Lost-result reconnect does not replay the old action.

**M2-02 — Session fence.** With queued input and pressed controls, reset or kill GameSession. Device connections close with code 4003; new welcome establishes the new session. Browser adapters explicitly rebind. Old connection/session/epoch messages and mismatched snapshots cannot establish authority. Restore the committed checkpoint paused, with no live leases or automatic resume.

**M2-03 — Subscription and snapshot ordering.** Publish a transition during view mounting, deliver snapshots out of order, and reconnect. Expected: subscribe-before-fetch plus revision checks preserve the newest permitted state. Unsolicited equal-revision duplicates are ignored; explicit bootstrap/request responses may refresh the view. Local progress animation cannot announce success.

**M2-04 — Persistence failure.** Use the initial 100 ms SQLite `busy_timeout`; hold a write lock and separately inject a write failure. Measure a bounded error path targeting less than the 400 ms input lease on the tested machine, without claiming hard real-time guarantees. No success, uncommitted state, or actuator effect may escape. Enter a volatile recovery pause with a `storage_error` diagnostic; retain the committed checkpoint. No transaction waits on the network. Record measured latency and configuration changes. Exercise each independent simulator SQLite store: expected-file missing/corrupt/version refusal, failures before/after commit, lost commit reply and crash/reload. Verify effective durability settings and measured latency without treating the busy timeout as a disk-I/O bound. Assert the exact version-one SQL constraints/checkpoint codec, singleton identity/version and per-record/whole-document limits; full journal, all reconciliation records, clear copies and retained service receipts must fit together. Reject implicit empty initialization and stale revision/hash writes. A late successful persistence completion after stop/rebind adopts history only and permits zero revived steps.

**M2-05 — Atomic winning transition.** Inject crashes before commit, after commit/before dispatch, and after dispatch/before acknowledgement. Before commit: no solved checkpoint or command. After commit: the restored checkpoint references the same durable `command_id`; no replacement ID or automatic replay. Recovery queries the box and preserves uncertainty when execution cannot be established. Complete commit-before-dispatch/unknown_command and accepted/interrupted recovery through explicit closed_no_replay, Reset and a new simulated round. The old identity/outcome remain, no old-ID redelivery or replacement command for the old solve occurs, and only the new solve creates a new intent. Assert the database one-solve unique key against the original game/session/round after several later recovery sessions; verify durable request hash/receipt readback and one-time dispatch claim without reconstructed win tickets.

**M2-06 — State separation and reconciliation.** Report `accepted`, `motion_complete`, `position_confirmed`, `uncertain`, and `failed` for the current command. Puzzle phase stays `solved`; neither motor completion nor latch confirmation implies an open lid. A null-command readiness report cannot overwrite persisted release intent. Pending/moving/uncertain outcome disables Pause/Reset until reconciled. Exercise protocol recovery preparation, persistent service inhibit, sealed all-motion evidence, mandatory boot/session fence, explicit host closure and local acknowledgement. Readiness alone cannot close an intent. Test valid terminal results, wrong identity, conflicting historical/current evidence, missing journals and unavailable server records. Inject failed writes/crashes/lost replies at each durable boundary; retry idempotently. Deliver original queued effects/envelopes throughout. Race Close against replacement preparation: only one generation wins, local invalidation alone cannot unseal, and old evidence is rejected. After Begin recovery, deliver a late terminal outcome and assert Reset still requires that recovery's host disposition; terminal observations cannot bypass active recovery. Run the same literal expected recovery traces through both simulator adapters with separate state/store/timing fixtures; expectation generation never invokes the model. Separately terminate transport, box runtime and GameSession and inspect persisted history and modeled-step counts. Adapter agreement alone cannot validate their shared semantics. Assert same-request Begin retry returns its original receipt after replacement, while a new replacement requires the expected prior recovery ID. Reseal after GameSession restart using current committed host context without rewriting the original preparation receipt. Append late/conflicting status evidence during checkpoint/Close persistence, including changed content at one status sequence; neither a disposition nor a stale full-state write can erase it or restore delivery.

**M2-07 — Transport boundaries.** Exercise missing credentials, spoofed class/identity, invalid enums/types/JSON, excessive nesting/strings, unsupported versions, fragmented messages, binary application frames, and size-limit plus-one cases. Enforce assembled-message limits of 4,096 bytes inbound/8,192 outbound, depth eight, and the documented 30-message/second rate with burst ten. Fail boundedly without crashing the game or creating atoms from received text. Run the production Elixir validator and later the identical native/ESP-IDF C++ parser/validator sources against the unchanged golden examples plus independent raw-byte/schema-branch cases in JSON_VALIDATION.md. Cover decoded duplicate keys (including escaped aliases/extensions), malformed UTF-8/surrogates, trailing roots, null-vs-missing, pool failure, exact safe-integer min/max/plus-one, integral decimal/exponent spellings and fractional precision traps such as 9007199254740990.5. Accept permitted top-level/capability extensions while rejecting strict nested additions. Reuse command/status sequences with changed extension content and reject the changed decoded message; object order, equivalent escapes and mathematically equal numeric spellings retain identical decoded comparison. Compare arbitrary extension numbers exactly without floats or the integer-only durable codec. Check outputs against the independent Draft 2020-12 oracle with exact numeric handling; agreement between production validators alone is insufficient.

**M2-08 — Backpressure and acknowledgements.** Slow a simulated connection and lose command/status acknowledgements. Snapshot coalescing stays bounded and does not discard required results. Status retries preserve sequence/content, apply no duplicate transition, and stop at the documented retry limit. Delayed cosmetic feedback neither repeats sound nor drives the motor. For WS and WSS separately, stop a controlled peer reading until instrumentation establishes real send backpressure within finite byte/time setup limits; account for TLS buffering and mark inability to induce pressure incomplete. Verify 100 ms socket send timeout, 200 ms complete-write and 100 ms teardown guards on the locked stack, bounded producer admission, one-write loop turns and deadline processing between several slow queued writes. Exercise data/control/upgrade paths, overflow, partial/error/timeout and late-success outcomes; retire the generation and never replay old envelopes after reconnect. Separately block a live transport stub beyond 1,500 ms in deterministic fake-box runtime tests: expire silence by the next bounded modeled step, deactivate motion and retain uncertainty without any successful send. Deliver completion before the queued watchdog message but after its deadline; it must not report success. Delay intent persistence past expiry and assert zero first steps; terminal/interruption I/O starts only after motion is inactive. Record actual WS/WSS scheduling/cleanup limits without claiming hard real-time guarantees. Deliver a write completion after its absolute deadline but before the queued timeout message: the runner must retire the generation and terminate the owner immediately, without a further close window. The additional 100 ms close allowance applies only to returned send errors/socket timeouts. Apply model deadline/persistence/effect-order assertions through both runtime adapters; preserve actual WS/WSS backpressure and blocked-Mint-owner evidence as separate external-client checks.

**Gate:** protocol simulators pass the contract, checkpoints survive process failure, and actuator uncertainty cannot become an automatic second action.

Attempt a mismatched chip/profile flash through the wrapper; it must refuse. Select serial ports explicitly. Record which binaries were compiled versus actually flashed. **M3-02 — Display/touch self-test.** On each physical terminal, verify corners, rotation, color order, coordinate mapping, and target hit boxes. Every play screen fits without scrolling. **M3-04 — End-to-end ownership.** Complete browser/browser, browser/CYD, CYD/browser, and CYD/CYD runs. Attempt a second claim and a queued old-owner action. The required player set never shrinks after disconnect; reconnection restores progress but waits for host resume and restored readiness.

**Gate:** two verified terminals run the shared game; browser fallback remains functional.

## M4 — Box bench and physical release

**M4-01 — Evidence gate.** Before connecting electronics, confirm the Samsung EP-TA20JWE's normal 5 V USB output at the chosen distribution point; do not request its alternative 9 V mode. Verify the identified ULN2003AN module's wiring and fitted-jumper function, 5 V motor requirement, input compatibility, common ground, protected mounting and accessible manual release. Route parallel power branches to the C5's documented input, driver and LED module; keep motor/LED current out of the 3.3 V regulator. Verify the service-USB source arrangement and documented isolation before connecting independently powered 5 V sources. Verify the Freenove WS2812 IN S/V/G connections, data-level interface (plan a 3.3 V-to-5 V buffer unless exact specifications establish adequate direct-drive margin), color order and bounded brightness before enabling LEDs. During staged bring-up, measure startup and simultaneous Wi-Fi/LED/motor stability with actual cables; 5 V / 2 A is a selected supply rating, not a completed load test. Before gameplay motion, record measured travel/rate/time limits, actual sensing, manual release and antenna clearance. Without the affected evidence, use a fake actuator; do not guess GPIOs, gear ratio, endpoint feedback or safe travel.

**M4-02 — Arming is permission.** With an unverified position, reject arming/release. Perform USB service calibration/reference and current locked-position verification; arm explicitly from the authorized host. Arm/disarm alone produces no steps. Reboot, disconnect, pause/session change, fault, and accepted actuation invalidate permission as specified. Retired arm IDs cannot be revived. Enter recovery with queued and reserved-before-first-step commands; persistent service inhibition rejects both. Seal recovery evidence and prove gameplay and USB jog/example/local stay blocked until the matching durable host disposition or replacement preparation is verified locally. Reboot preserves inhibition/freeze but invalidates old evidence bindings.

**Local service contract checks for M4-02.** Implement [LOCAL_SERVICE_V1.md](LOCAL_SERVICE_V1.md) through the shared firmware decoder and both wrappers. Test every exact command/args/result shape; request/response byte, depth, member, string and page limits; duplicate keys; retained receipt/sequence/CAS behavior and receipt expiry without reexecution. Inject lost replies/crashes at provision, entry, seal, acknowledgement, replacement, clear authorization/erase/fence and exit. Retain operation IDs and complete clear authorization through erasure; inspect all 32 entries one page at a time and the separate absent-ID record. Exercise lost-host-key stop with unavailable host authorization, current-session refresh/reseal after GameSession restart, and terminal observations after recovery begins. Reject direct service exit while frozen or before fresh post-preparation verification; require deliberate authorized unfreeze, fresh reference/locked readiness, then a durable exit that retains the false freeze. Apply the same gate to labeled simulated preparation without physical-position claims. Never automatically retry motion or treat local present position as historical execution proof. Verify all physical profile/electrical/calibration gates independently; no-sensor homing produces zero steps. Record host-fake and physical results separately.

**M4-03 — Durable acceptance and freshness.** Inject NVS failure, stale boot/session/connection/arm, and expired command challenge before acceptance and immediately before the first step. No unauthorized step occurs. A valid command is recorded before movement, consumes its arm, and executes only within measured travel/rate and duration bounds.

**M4-04 — Duplicate and journal capacity.** In a firmware host test, accept 32 distinct command IDs; request a 33rd. Expected: `history_full`, no eviction, no movement. Existing duplicates return outcomes without stepping; changed fingerprints fail. Reboot, then query the first ID using current transport credentials: its durable outcome remains available. Unreconciled uncertain records prevent history clearing; separate local administrative metadata never rewrites their execution outcome. Authorized USB clearing requires reconciliation, stopped/disarmed hardware, reboot, and a new host session. Reconcile uncertain entries at capacity without a 33rd accepted slot; an absent queried ID uses one bounded external recovery record. Refuse clearing without matching local attestations of durable host dispositions. Inject faults before/after clear-pending persistence and during erase; retain inhibition and require reboot plus a different host session. Reset retains every entry; deliberate clearing preserves server history and never validates old envelopes. Erase per-entry reconciliation metadata and reboot: the versioned external clear authorization must retain matching verified dispositions/acknowledgements and permit the defined fence, unfreeze, preparation, verification, service-exit and arm sequence without reconstruction. Interrupt each step; missing/corrupt/unsupported required record versions remain inhibited.

**M4-05 — Interrupted motion.** Cut connectivity, create authenticated-server silence, and power-cycle before/after first movement and before final recording. Known close stops at the next step boundary; silence stops within 1,500 ms plus one bounded step interval. Coils turn off. Report uncertain/unknown where appropriate; reconnect and boot never resume, unlock, home, or relock automatically. Also enter local service while moving, stop at a bounded boundary and disable outputs before successful acknowledgement. Fail inhibit/seal/attestation writes and reboot; gameplay remains blocked. Complete explicit administrative recovery and a newly verified round without changing the old uncertain outcome or resending the original ID. Validate actual physical behavior separately from host fakes.

**M4-06 — Limits and truthful results.** Exercise release-travel, speed and motion-timeout limits without deliberately damaging the mechanism; these bounds are always required. Exercise homing-travel/deadline limits and home-sensor faults only when a home sensor is installed, verified and homing is enabled. Otherwise homing is unavailable and the explicit manual-reference workflow applies. The default design stroke is at most three seconds; absolute motion timeout is eight seconds. Unsensed completion stays `motion_complete`/unverified. A single home switch cannot establish the opposite endpoint; manual verification requires an actual current observation. If an optional lid button is considered, verify its contacts, momentary behavior and mounting separately; lid seated/contact released is not latch position, cannot supply `position_basis:"endstop"`, and adds no version 1 field or automatic motor action.

**Gate:** one bounded bench release and fault recovery are physically demonstrated. Puzzle reset is a host action; physical relocking uses local USB/serial maintenance. Neither reset nor reconnection moves the mechanism.

## M5 — Cardboard-box integration, demonstration, and handoff

**M5-01 — Installed mechanism.** Before permanent mounting, dry-fit the complete assembly inside the green PASCAL hinged rigid cardboard box's user-reported nominal **90 mm W × 85 mm D × 70 mm H** envelope. Include the actual C5, driver, motor/mounting ears, shaft/coupler, full cam sweep, LED board, connectors, cable bends, reinforcement, any false floor and intended prize. Record actual fit; nominal dimensions alone do not establish hole locations, false-floor height or prize volume. Use rigid/load-spreading motor and catch mounts, hinge/cam cable clearance and strain relief; keep the manual release accessible with the lid closed and feedback visible. After mounting, repeat alignment/calibrated travel, clearance, manual release, insulation, 5 V/load stability, antenna clearance and closed-lid radio checks, then the actual game-to-release sequence. Cardboard does not require the antenna to be outside. Complete ten bench release/local-service-reset cycles without a jam. Retest further only to investigate a concrete failure or changed assembly.

**M5-02 — Connected run.** Observe a 30-minute session with several disconnect/reconnect cycles. Record memory/queue behavior, watchdog resets, stale-input handling, and any display stalls. No progressive memory growth or unexplained reboot is acceptable. Preserve the browser-only demonstration if a physical issue remains blocked.

**M5-03 — Interview demonstration.** Show normal cooperative play, the partial player views versus host view, one controller disconnect with preserved progress, and a GameSession restart-to-paused recovery. Explain what the process owns, what persistence restores, and why an uncertain command is not replayed. Use a simulated actuator for destructive failure injection.

**M5-04 — Actual results report.** Update `docs/implementation-status.md` with case IDs, status, Git revision, exact commands, dates, runtime/firmware/profile versions, device identity, observed results, and evidence paths. Redact secrets. List each blocked verification and its specific missing evidence. Document setup, LAN binding, provisioning, flash, USB service, arming, run, shutdown, recovery, and manual release. Do not mark planned checks as passed.

**Final gate:** deliver a runnable, documented game and an honest verification record. Every physical claim must trace to observed hardware evidence; every remaining limitation must be explicit.
